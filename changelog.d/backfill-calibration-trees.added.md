Add the `backfill-calibration-trees` operator command, which fills the collector's calibration tree store with every build production's public tree manifest lists, before the dashboard reads trees from that store. `--production-manifest-url` (required, `https`) is the dashboard's `https://<dashboard>/api/microcosm/tree-manifest`, which the command requests for each country (`--country`, repeatable; every country by default) with no credential and no redirect followed, through its own client. An answer that isn't HTTP 200, is over 16 MiB, takes over 2 minutes to arrive, isn't JSON, has another schema version or country, or names a latest build that isn't one of its release builds is an `error` for that country only. Each entry is checked before any of its values is used in a Hugging Face path (kind, the country's repo, a 40-hex commit, a `<release>` or `<release>/<build>` release ID and directory, a staging run that is one safe name and not `latest`, a publication time with an offset or none, a label), and an entry that fails is `invalid` while the rest continue. A release build is read from `releases/<releaseDirectory or releaseId>/` at its commit, with its build manifest, release manifest and demographics null when absent; a staging build follows only the staging readers' rules that locate files: a run's declared diagnostics path with its SHA-256 (or, for a schema-1 run, `runs/<id>/calibration_diagnostics.json`) with its build and release manifests, a staged bundle named by a run's `staged_dataset` receipt, or a staged bundle in the release repo. Each tree records production's release ID or run, label, repo, commit and publication time. Only production's latest entry asks to become its country's latest, and each country's latest is built first; production's latest already stored but not the store's latest is published again exactly as stored, from its files at the stored commit with the stored repo and time, so only the latest moves, and one that already is the store's latest needs no work. The store's manifest is read once, with the tree package's new read-only `src/calibration-tree-manifest-read.ts`; an entry the store holds with the same commit and time (to the millisecond) is `already_stored`, with another `mismatch`, and neither downloads anything. Builds run one at a time, each in a removed temporary directory, through the tree handler's shared `build_and_publish`: a file over 256 MiB is `too_large` from its listing, each file is streamed to disk with the new `HuggingFaceReader.download_file` and checked against its listing, the worker runs without the Blob token, and the manifest lock is held only around the publication. Worker and publication exit 2 are `unbuildable` and `refused`; any other failure is `error`, and the next build still runs; no build starts after 40 minutes (`deferred`). Each entry's document says whether its build ID matches production's; staging build IDs are expected to differ, since the worker hashes 4 of a staging build's source files where the GitHub Actions publisher hashes 7. The summary gives the counts, whether the run is incomplete, how many release builds differ from production, and each country's latest. The command exits 1 when anything is `error` or `deferred`, a country failed, or a country's latest wasn't made the store's latest, and 2 for an argument error. `--kind` limits it to release or staging builds, and `--dry-run` reads production's manifest, the Hugging Face listings and the store's manifest, and downloads no diagnostics, runs no tree worker and takes no lock. It needs `DATABASE_URL`, `COLLECTOR_HF_READ_TOKEN` and `COLLECTOR_CALIBRATION_TREE_BLOB_TOKEN`, so it runs as an execution of the worker job with its arguments overridden. `HuggingFaceReader` also gains `list_folder`, and a failed read now carries Hugging Face's `X-Error-Code` (`HuggingFaceReadError.error_code`).
